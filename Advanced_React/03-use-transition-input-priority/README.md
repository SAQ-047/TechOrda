# 03. Приоритет ввода через useTransition

[Папка решения на GitHub](https://github.com/SAQ-047/TechOrda/tree/main/Advanced_React/03-use-transition-input-priority).

Самостоятельная версия лаборатории поиска из условия. Данные и нагрузка одинаковы в обоих режимах: 240 вымышленных элементов `React / CSS / TypeScript`, по 80 000 итераций в каждой отображаемой карточке. Массив создаётся вне компонента; расчёт checksum остаётся в `CourseCard`, а граница `memo` — вокруг `Results`.

## Устройство обновлений

Управляемый input получает `value={text}`. Обработчик всегда вызывает `setText(nextText)` вне transition. В обычном режиме `setListQuery(nextText)` также выполняется срочно. В transition-режиме только обновление `listQuery` находится внутри `startTransition`.

При срочном обновлении `text` прежний строковый prop `query` позволяет `memo(Results)` пропустить повторное вычисление дорогого списка. При обработке нового `listQuery` React вычисляет карточки. Отдельные `CourseCard` дают React границы, между которыми можно уступить выполнение более срочной работе. Один уже выполняющийся синхронный цикл внутри карточки не прерывается посередине.

`isPending` явно показан как `true / false`, а область списка получает `aria-busy`. Пока transition не завершён, могут отображаться прежние результаты. Над списком показан запрос именно завершённого DOM списка; рядом с input — срочный `text`. Их можно сравнить при быстром вводе.

Кнопка «Очистить» вызывает тот же обработчик с пустой строкой. В обработчик передаётся захваченное значение `nextText`; внутри transition не читаются событие или устаревший `text`. Поэтому последнее обновление, включая `''`, становится запросом готового списка. Пустой запрос возвращает все 240 карточек.

Дорогая фильтрация и карточки не вычисляются внутри callback `startTransition`: он помечает обновление состояния, а не переносит произвольный синхронный код в другой поток. Отдельного таймера, debounce или Effect для синхронизации двух состояний нет.

## Сравнение режимов

Для ручного сравнения используйте production-preview, одинаковое замедление CPU в DevTools и одну последовательность: очистить → быстро набрать `React` → дождаться списка → очистить. Повторите её в режиме «Обычный» и «Transition». Не меняйте данные, число итераций или границы компонентов между опытами.

Проверено 9 ноября 2026 года в headless Brave, в production-preview, с одинаковым замедлением CPU ×6. Перед опытом выполнялся прогрев запросом `CSS` и очисткой. В каждом режиме трижды вводилось `React` без намеренной задержки между клавишами, всего по 15 событий ввода. Между попытками список полностью очищался до исходных 240 элементов.

| Наблюдение | Обычный режим | Transition |
| --- | --- | --- |
| Медиана от события input до фиксации React text в DOM | 45,3 мс | 1,9 мс |
| Наблюдался `isPending: true` | Нет | Да |
| Зафиксированы промежуточные состояния: новый text, прежний запрос списка | 0 | 15 |
| Итоговый запрос и результат каждого ввода | `React`, 80 карточек | `React`, 80 карточек |

В обычном режиме срочный text и список фиксировались вместе. В transition-режиме React сначала фиксировал новый text с прежними результатами, показывал pending, затем фиксировал готовый список. Измерялась задержка до уведомления MutationObserver о React text в DOM; это не время отрисовки кадра и не полное время вычисления списка. Числа относятся к этому локальному опыту и не задают коэффициент ускорения. Версия браузера, задержки по попыткам и примеры состояний сохранены в [comparison.json](comparison.json).

Transition меняет приоритет работы, но не уменьшает число итераций отдельной карточки и не гарантирует фиксированного ускорения. На быстром устройстве индикатор может быть кратким. При прерывании фонового render часть работы может быть выполнена повторно, поэтому общее время завершения списка может не уменьшиться. Dev-режим с корневым StrictMode дополнительно вызывает компоненты; его измерения нельзя напрямую сравнивать с production.

## Версии и самопроверка

React / React DOM 19.3.1, Vite 8.3.6, @vitejs/plugin-react 6.3.0. Проверка на Node.js 20.20.2 и npm 10.9.4. Версии закреплены в общем [package.json](../package.json), дерево зависимостей — в [package-lock.json](../package-lock.json).

Команды `npm ci` и `npm run build` прошли. Сценарии в Brave проверены через Playwright Core.

| Сценарий | Dev + StrictMode | Production |
| --- | --- | --- |
| Оба режима: `React`, `CSS`, `TypeScript`, разный регистр, частичный запрос, отсутствие совпадений, пустая строка | PASS | PASS |
| Быстрый ввод и последний запрос `React 23` | Последний запрос, 3 карточки | То же |
| Кнопка очистки и очистка самого input | Пустой запрос, 240 карточек | То же |
| Очистка во время `isPending: true` | Срочный text и готовый список в итоге пустые, 240 карточек | То же |
| Ошибки JavaScript и загрузки ресурсов | 0 | 0 |
| Экран 360 px | Горизонтальной прокрутки нет | То же |

В проверке очистки во время pending сначала зафиксирован `text = TypeScript` с ещё пустым запросом старого списка; затем нажата «Очистить» до завершения transition. Устаревший непустой запрос не вернулся.
