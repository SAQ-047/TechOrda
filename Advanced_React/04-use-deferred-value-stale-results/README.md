## Состояние и подпись списка

Поисковое состояние одно: `text`. Управляемый input обновляет его обычным `setText`. Отложенная версия получается через `const deferredText = useDeferredValue(text)`; отдельного `listQuery` с setter, transition, Effect или таймера здесь нет.

В deferred-режиме `query = deferredText`, в обычном — `query = text`. Хук вызывается безусловно по правилам hooks; обычный режим не использует его отложенный результат. Проверка `text !== query` показывает именно отставание отображаемого списка, а не неиспользуемого значения в обычном режиме.

Единственный prop списка — `query`: `<Results query={query} />`. Свежий `text`, флаг устаревания, новые объекты или callbacks в список не передаются. При срочном обновлении ввода прежний строковый prop позволяет `memo` пропустить вычисление дорогих карточек.

Подпись «Результаты для запроса» находится **внутри Results** и использует тот же `query`, что фильтрация и карточки. Поэтому старые результаты подписаны прежним запросом. Снаружи при несовпадении текущего ввода и запроса списка показано ровно «Обновляем результаты», область получает `aria-busy`, карточки приглушены. При совпадении показано «Результаты актуальны».

Очистка меняет только `text` на `''`. Пока список догоняет ввод, его прежняя подпись остаётся корректной. После завершения показаны пустой запрос и все 240 карточек.

## Отличие от debounce

Типичный debounce ждёт заданную паузу после последнего события ввода, перезапуская таймер при каждом новом событии. `useDeferredValue` не задаёт интервал ожидания: React начинает фоновое обновление, когда может уступить ему выполнение после срочной работы, и может перезапустить его при новом вводе. На быстром устройстве отставание может быть почти незаметно; это не фиксированная задержка и не гарантия ускорения расчёта.

## Ограничение длинного синхронного цикла

React может уступать выполнение между компонентами, но не прерывает JavaScript посередине уже выполняющегося цикла карточки. Если весь дорогой расчёт поместить в один длинный синхронный цикл, он продолжит блокировать главный поток и обработку ввода; `useDeferredValue` не превращает его в параллельную работу. В этой лаборатории нагрузка распределена по отдельным карточкам. Для одного монолитного расчёта нужны разбиение работы на порции или Web Worker.

## Ручное наблюдение

Откройте production-preview и выберите одинаковое замедление CPU в DevTools, например ×6. В режиме `useDeferredValue` введите `React`, дождитесь результатов, затем замените ввод на `CSS`. Пока показано «Обновляем результаты», текущий ввод уже может быть `CSS`, а подпись списка и карточки всё ещё относятся к `React`. Затем они вместе сменятся на `CSS`. Повторите опыт с очисткой и с обычным режимом.

## Версии и самопроверка

React / React DOM 19.3.1, Vite 8.3.6, @vitejs/plugin-react 6.3.0. Проверка на Node.js 20.20.2 и npm 10.9.4. Версии закреплены в общем [package.json](../package.json), дерево зависимостей — в [package-lock.json](../package-lock.json).

Проверено 9 ноября 2026 года: `npm ci` и сборка всех четырёх workspaces прошли. Браузерная проверка выполнялась через Playwright Core и установленный Brave в dev + StrictMode и production. Для наблюдения промежуточных состояний использовалось одинаковое замедление CPU ×6.

В обеих сборках зафиксирована последовательность:

| Текущий text | Подпись запроса списка | Показанные карточки | Статус |
| --- | --- | --- | --- |
| `React` | `React` | 80 React | Результаты актуальны |
| `CSS` | `React` | Прежние 80 React | Обновляем результаты |
| `CSS` | `CSS` | 80 CSS | Результаты актуальны |

При отставании сохранена идентичность первой старой карточки. Для каждого наблюдаемого DOM-состояния проверены подпись, все названия карточек и условие индикатора: строки соответствуют запросу подписи, а «Обновляем результаты» показано ровно при `text !== query`. В обычном режиме промежуточного отставания списка не зафиксировано.

Также проверены:

- Оба режима: `React`, `CSS`, `TypeScript`, разный регистр, частичный запрос, отсутствие совпадений и пустая строка — правильный состав и порядок элементов.
- Быстрый ввод с последним запросом `React 23` — три нужные карточки.
- Очистка через input и кнопку — пустая строка и 240 карточек.
- Очистка во время отставания: после `CSS → TypeScript` кнопка нажата при старом списке CSS. Затем текущий text уже пустой, подпись всё ещё CSS и показано «Обновляем результаты»; в итоге запрос списка пустой, показаны 240 элементов. Старый запрос не возвращается.
- Ошибок JavaScript и загрузки ресурсов нет; на экране 360 px горизонтальная прокрутка отсутствует.

Все сценарии — **PASS** в dev и production. Проверочный сценарий выполнялся отдельно, тестовый runner в учебный проект не добавлен.
